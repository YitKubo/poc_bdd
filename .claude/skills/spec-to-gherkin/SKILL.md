# 仕様 → Gherkin

仕様書や口頭の説明から、`tests/features/<名前>.feature` を作る（**既存の feature にシナリオを追加するときも**この手順で行う）。
合否を決めるテストなので、**具体的な値**で書く。

## 手順

1. **入力を読む**
   - 仕様書のパスが渡されたら読む。無ければ会話の内容を元にする
   - 既存の `tests/features/*.feature` と `tests/steps/common_steps.py` を読み、使えるステップを把握する
2. **あいまいな点を確認する**（推測で埋めない）
   - 数値のしきい値と単位、「以上」か「超え」か（境界を含むか）
   - 時間条件（何 ms 続いたら、連続か累計か）
   - 異常時・復帰時の振る舞い
   - **仕様書の表・文章、または既存の feature から決まることは、質問しない**。決まらないことだけを質問する
   - 「決まる」の基準: **シナリオが確かめる振る舞いそのもの**が、仕様書の文章・表・状態遷移図に書かれていること。
     別の振る舞いの記述からの類推は「決まる」に入れない
     （例: 仕様書に検出側の「途切れたら数え直す」しかないとき、解除側の数え直しは類推なので決まらない）
   - 質問できない（非対話で動いている）ときは、決まらない点を最終報告に「要確認」として書き、
     **その点のシナリオは作らない**（仕様書に無い振る舞いを feature にしない）。決まる範囲だけで進める。
     作ったシナリオには、どの文を根拠にしたかを報告に書く
   - 仕様書が無い場合は、ここで決まった内容を `docs/specs/<名前>.md` の下書き（目的・振る舞い・パラメータ表）にして先に作る
3. **シナリオを設計する**
   - 代表的な流れ 1 本（時間で状態が変わる機能だけ。`@代表動作` タグを付ける）。
     **タグを付けるのはこの 1 本だけ**。境界値の Outline や、後から追加したシナリオには付けない
   - 境界値・異常系は `Scenario Outline` + `Examples:` の表にする。
     **境界の両側に、それぞれ最低 1 値**（境界ちょうどを含む。例: 1500 rpm 超えなら 1500 と 1501）。値の刻みは、仕様の単位の最小（整数なら 1）
   - 1 シナリオ 1 振る舞い。「経過する」は、**`Then` で区切った段ごとに数える**（`And` で続く行は別々の 1 回）。
     1 つの段に「経過する」が 2 回以上出る長い流れは分割する。
     前提状態の確認を挟んだ状態遷移のシナリオは、全体で 3 回以上になってよい（段ごとに 1 回なら分割しない）
   - **状態が変わること（復帰・解除・継続）を確かめるシナリオは、変える前の状態を `Then` で確かめる**。
     確かめないと、そもそも変わる前の状態になっていなくても、期待値が `OFF` や「なし」のシナリオは通ってしまう
   - **既存の feature に追加するとき**: シナリオは末尾に足す。既存と同じ振る舞いのシナリオは作らず、
     既存のシナリオを広げるなら Examples に行を足す。Feature の説明文は、新しいしきい値が増えたときだけ更新する
4. **feature を書く**（下のルールに従う）
5. **整形して確認する**: `docker compose run --rm dev make fmt` → `docker compose run --rm dev make chart` → `make docker-lint`
   （チャートが出れば、ステップの形が正しい。`git status` で新しく増えた `charts/` は、**例の行ごと**に 1 組。`make lint` はホストでは動かない）
6. 作った feature の一覧と、足りないステップがあれば知らせる。次を案内する
   - `gherkin-to-pytest`（ステップとテスト。`docker compose run --rm test` で通るかは、そこで確かめる）
   - `chart-review`（チャートの確認）
   - `charts/` は feature と一緒にコミットする（CLAUDE.md 参照）

## 書き方のルール

- 1 行目は `# 仕様: docs/specs/<名前>.md`（キーワードは英語、ステップ文・シナリオ名・説明文は日本語。英語は既定の言語なので `# language: en` は書かない。reformat-gherkin が消す）
- キーワード: `Feature` `Background` `Scenario` `Scenario Outline` `Examples` `Given` `When` `Then` `And`
- **ステップの形を揃える**（そのままタイミングチャートに変換されるため）
  - 信号: `〇〇が "値 単位" である`（例: `エンジン回転数が "3000 rpm" である`、`燃料カットが "ON" である`）
  - 時間: `"N ms" 経過する`（N は 10 の倍数）
  - **値（数値・単位・ON/OFF・DTC）は必ずダブルクォートで囲む**。数値と単位の間は半角スペース。アウトラインは `"<rpm> rpm"`
- `Given` は初期状態、`When` は途中の変化・操作、`Then` は出力の確認にだけ使う（入力の変化を `When` に続けて書いてよい）
- 出力の確認の前に、必ず `"10 ms" 経過する` 以上の時間を進める
- 値はすべて仕様書のパラメータ表から取る。仕様書に無い数値を作らない
- 既存のステップの言い回しを優先する。新しい信号が必要なら、言い回しを同じ形にして新しく作る
- `Examples` の表には「備考」列を付けてよい（人が読む説明。ステップからは参照せず、チャートの題名からも除かれる）

## 例

```gherkin
# 仕様: docs/specs/rev_limiter.md
Feature: レブリミッタ
  エンジン回転数が上限に達したら燃料をカットする。

  Background:
    Given ECUが初期化されている

  Scenario Outline: カット開始条件
    Given エンジン回転数が "<rpm> rpm" である
    When "10 ms" 経過する
    Then 燃料カットが "<state>" である

    Examples:
      | rpm  | state |
      | 6499 | OFF   |
      | 6500 | ON    |
```
