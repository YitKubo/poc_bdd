# チャートの AI 確認

機械的な変換（gherkin2puml）は文の形しか見ない。図が仕様どおりか・人が読めるかは、表で突き合わせて確認する。
**合否は決めない**（合否は feature のテストだけ）。指摘するだけ。

## 実行の種類

- **確認だけ**（既定）: ファイルを直さない・コミットしない。報告まで。「確認して」「レビューして」と頼まれたとき
- **確認して直す**: 手順 8 まで行う。直してよいと言われたときだけ

## 手順

1. `make docker-chart` で `charts/` を最新にする
2. 対象の `docs/specs/<名前>.md`、`tests/features/<名前>.feature` を読む
3. **`.puml` の値と時刻を読む**。ファイルが多いので、定型行を除いて Bash でまとめて出してよい。
   全機能なら `charts/*/*.puml`、1 機能なら `charts/<名前>/*.puml` にする。例:

   ```bash
   for f in charts/*/*.puml; do echo "## $(basename "$(dirname "$f")") / $(basename "$f" .puml)"; \
     grep -v '^@startuml\|^@enduml\|skinparam\|^scale\|^legend\|^endlegend\|ECUが初期化\|^$' "$f" | tr '\n' ' '; echo; done
   ```

   `Scenario Outline` の図は、feature の `Examples` の行と値が一致しているかを、すべて確かめる
4. **仕様の項目を洗い出す**: 仕様書のパラメータ表と振る舞いの文から、確認すべき項目を行にして書き出す
   - 各しきい値の境界の両側（「以上」「超え」の違いを含む）、時間条件（N ms 未満 / ちょうど）、復帰・解除、異常時
5. **項目ごとに feature と図を探して突き合わせ、次の表を作る**

   | 仕様の項目 | シナリオ（feature） | 図（.puml の値と時刻） | 判定 | 備考・重要度 |
   |---|---|---|---|---|

   判定は ○（一致）/ ×（食い違い）/ 漏れ（対応するシナリオがない、または確かめ方が足りない）。
   「範囲外（別の仕様）」「間接確認のみ」は判定に ○ を付けず、備考に書く
   （例: 「代表動作で間接的に確認」「範囲外: ect_sensor_diag の仕様」。他の機能との接続は、その機能の確認で見る）。
   重要度は 高 / 軽微。1 項目ずつ見る点:
   - **値と単位**: 入力・期待値が仕様書の表の値と同じか。数値を feature が勝手に作っていないか
   - **時刻**: `.puml` の `@t` と確認の位置が、feature の「N ms 経過する」の合計と合っているか
   - **期待値**: 確認する出力の値が、仕様の振る舞いから導かれる値と合っているか（ON/OFF の取り違えなど）
   - **前提状態の確認**: 復帰・解除・継続を確かめるシナリオが、変える前の状態を確かめているか。
     確かめていないと、期待値が `OFF` や「なし」のシナリオは、変わる前の状態になっていなくても通ってしまう（漏れ・高）。
     **原因が同じ行は 1 件にまとめ**、該当するシナリオと行を列挙する
   - **漏れ**: 仕様書にあるのに、どのシナリオにも出てこない行。
     **仕様書に書かれていない振る舞い**（例: 解除側の数え直し、状態を保つ向きが片方だけ書かれているときの逆の向き）は
     漏れに数えず、「仕様書に明記なし（要確認）」として別に報告する
6. **PNG を Read で開いて、図として読めるか見る**。`.puml` の値の確認とは別に、人が図を見て分かるかを見る
   - 開く枚数: **各機能の `@代表動作` の図は全部**。`Scenario Outline` の図は、**「形」ごとに先頭 1 枚**と、**境界値・異常系を各 1 枚以上**
     （異常系が無い機能は境界値だけでよい）。形とは、信号の種類（波形か帯か）と確認の本数の組み合わせ。
     1 機能あたり、代表動作を除いて 8 枚までを目安にする。開いた枚数と、開かなかった理由を報告に書く
   - PNG は Read でそのまま開ける（パスに日本語・括弧があってもよい）。開けないときだけ、別の場所に連番でコピーして開く
   - 見る点（下の「指摘と許容の線引き」を使う）:
     信号名や値の文字切れ・重なり、時間軸、確認の帯が見えるか、信号の並び順、
     **数値の波形で中間値が読めるか**（軸のラベルは最小値と最大値だけ）
7. 結果を機能ごとに、5 の表と「見にくさの指摘」で報告する。×・漏れ・要確認は、直す場所を切り分けて提案する
   - 図の見え方 → `tools/gherkin2puml.py`
   - シナリオの組み立て・漏れ → feature（`spec-to-gherkin`）
   - 仕様と feature の食い違い、仕様書に明記なし → どちらが正しいかをユーザーに確認する（勝手に直さない）
8. （「確認して直す」のときだけ）直したら `make docker-chart` で再生成し、`charts/` を feature と一緒にコミットする

## 図の読み方（gherkin2puml の描き方）

- 入力は波形（数値）か帯（ON/OFF・値が変わらないもの）。出力は常に文字の帯で、確認する前は「?」
- 黄色の「確認」の帯は、期待値を確認する時点から始まる。帯の中で期待値が始まっていればよい
- 確認の**直後**に変わる入力は、帯の幅だけ後ろにずらして描かれる（確認と同時刻に描くと、その値で確認したように見えるため）
- 時間軸の右側が空白なのは、PlantUML が軸を最後の時刻の約 2 倍まで伸ばすため（不具合ではない）

## 指摘と許容の線引き

| 状況 | 扱い |
|---|---|
| 時刻が近い確認で「確認」の文字が重なるが、値と時刻は読める | 許容（備考に書くだけ） |
| 数値の波形の中間値（6400 rpm など）が PNG から読めない | 指摘（軽微）。値が `.puml` で確認できても書く |
| 値や時刻が PNG からも `.puml` からも読めない | 指摘（高） |
| 文字が帯の縁や遷移の線に隣接して欠ける・重なるが、読める | 指摘（軽微） |
| 信号名が切れる | 指摘（軽微） |
| 1 つの図で複数の中間値が読めない（1200 と 1100 など） | 読めない値ごとではなく、図ごとに 1 件（軽微） |

## 注意

- 見えたものだけを報告する。読み取れない部分は「読み取れない」と書く
- 表の ○ は、実際に値を照らしたものにだけ付ける
